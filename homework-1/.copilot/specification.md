# Banking Transactions API Specification

## 1. Purpose
This document defines the functional and non-functional specification for the Homework 1 Banking Transactions API implementation in this repository.

The API provides:
- Transaction creation
- Transaction retrieval and filtering
- Account balance calculation
- Account summary calculation

## 2. Scope
In scope:
- REST API over HTTP
- In-memory transaction storage
- Validation and structured error responses
- Request tracing and structured logging

Out of scope:
- Persistent database storage
- Authentication and authorization
- Idempotency guarantees
- Distributed transactions

## 3. Technology Constraints
- Language: Go 1.23+
- HTTP framework: Fiber v2
- ID generation: UUID v4
- Logging: Go standard library slog (JSON output)
- API documentation: OpenAPI 3 generated by Swaggo from code annotations
- Test assertions: Testify (assert/require)
- Runtime: local Go or Docker

## 4. Architecture
Hexagonal architecture with clear boundaries:
- Domain: business entities and domain errors
- Ports (in): use case interface
- Ports (out): repository interface
- Service: business logic and validation orchestration
- Adapters in: HTTP handlers
- Adapters out: in-memory repository
- Bootstrap: server setup and dependency wiring
- Documentation flow: annotations in handlers/bootstrap -> generated docs/swagger.yaml

Primary implementation paths:
- src/cmd/api
- src/internal/domain
- src/internal/ports/in
- src/internal/ports/out
- src/internal/service
- src/internal/adapters/in/http
- src/internal/adapters/out/memory
- src/pkg/errorhandler
- src/pkg/middleware
- src/pkg/logger
- scripts/generate-swagger.sh
- docs/swagger.yaml

## 5. Data Model
Transaction:
- id: string (auto-generated UUID)
- fromAccount: string (ACC-XXXXX)
- toAccount: string (ACC-XXXXX, required for transfer)
- amount: number (> 0, max 2 decimals)
- currency: string (ISO 4217 whitelist)
- type: deposit | withdrawal | transfer
- timestamp: ISO 8601 UTC datetime
- status: pending | completed | failed

AccountBalance:
- accountId: string
- balance: number
- currency: string

AccountSummary:
- accountId: string
- totalDeposits: number
- totalWithdrawals: number
- transactionCount: integer
- lastTransactionDate: ISO 8601 UTC datetime

## 6. Functional Requirements
FR-1 Create Transaction
- Endpoint: POST /transactions
- Behavior:
- Validates request body fields
- Creates transaction with generated id and UTC timestamp
- Stores transaction in memory
- Returns 201 with created transaction

FR-2 List Transactions
- Endpoint: GET /transactions
- Behavior:
- Returns all transactions when no filters are provided
- Supports optional filters:
- accountId: matches fromAccount or toAccount
- type: deposit | withdrawal | transfer
- from: YYYY-MM-DD (inclusive)
- to: YYYY-MM-DD (inclusive to end of day)

FR-3 Get Transaction By ID
- Endpoint: GET /transactions/:id
- Behavior:
- Returns matching transaction
- Returns 404 if not found

FR-4 Get Account Balance
- Endpoint: GET /accounts/:accountId/balance
- Behavior:
- Computes balance from completed transactions
- Transfer affects both source and destination account
- Returns 404 when no transactions exist for account

FR-5 Get Account Summary
- Endpoint: GET /accounts/:accountId/summary
- Behavior:
- Returns totals, count, and last transaction timestamp
- Returns 404 when no transactions exist for account

FR-6 Health Check
- Endpoint: GET /health
- Behavior:
- Returns 200 with {"status":"ok"}

## 7. Validation Rules
- amount must be positive and have at most 2 decimal places
- fromAccount must match regex ^ACC-[A-Z0-9]{5}$ (case-insensitive)
- toAccount must match same regex for transfer type
- currency must be in allowed ISO 4217 subset
- type must be one of deposit, withdrawal, transfer
- invalid JSON body returns 400
- invalid date query format for from/to returns 400

## 8. API Endpoints and Status Codes
- POST /transactions: 201, 400, 422
- GET /transactions: 200, 400
- GET /transactions/:id: 200, 404
- GET /accounts/:accountId/balance: 200, 404
- GET /accounts/:accountId/summary: 200, 404
- GET /health: 200

## 9. Error Contract
All error responses follow:
{
  "error": "human-readable message",
  "request_id": "string",
  "details": []
}

Validation errors (422) include field-level details:
{
  "error": "Validation failed",
  "request_id": "string",
  "details": [
    {"field": "amount", "message": "must be a positive number"}
  ]
}

## 10. Non-Functional Requirements
- Thread safety for in-memory storage via RWMutex
- Structured JSON logging per request
- Request correlation via X-Request-ID
- Centralized error handling and panic recovery
- Portable execution via Docker
- API documentation must stay in sync with code through annotation-based generation
- Docker Compose should expose API and Swagger UI together

## 11. Documentation and Runtime Operations
- Generate API documentation:
  - Run ./scripts/generate-swagger.sh from the repository root
  - Output file: docs/swagger.yaml
- Run services with Docker Compose:
  - API: http://localhost:8080
  - Swagger UI: http://localhost:8081
  - Compose uses docs/swagger.yaml mounted into the swagger-ui container
- Runtime Docker image must remain focused on API runtime only (no swagger generation in Dockerfile)

## 12. Assumptions
- Single service process runtime
- In-memory data resets on restart
- No multi-currency conversion logic
- No business rules for overdraft or account state

## 13. Acceptance Criteria
- Service starts successfully on configured port
- All required endpoints respond with expected status codes
- Validation rules are enforced with structured errors
- Filtering works for accountId, type, from, and to
- Balance and summary endpoints return correct derived values
- Logs include request_id, method, path, status, and latency
- Docker and local run flows are documented and functional
- OpenAPI documentation is generated successfully from source annotations
- Docker Compose starts both API and Swagger UI
- Automated tests pass with coverage target >= 85%
